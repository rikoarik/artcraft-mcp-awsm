# Prompt to evidence-backed direction

The user supplies an ordinary product request, not a design-system questionnaire.
Own color, type, icons, imagery, background treatment, layout and routine motion.
Respect supplied constraints. Ask only when missing product facts or an ambiguous
write target would materially change the work. Do not ask the user to browse fonts
or select icon families. Offer a concise recommended direction with optional
alternatives when useful; do not block progress on aesthetic choices.

## Inspect before recommending

1. Inspect the existing entry page, tokens, assets and components. For edits, keep
recognizable branding and successful interactions. Read the product brief and real
content: what the product does, who uses it, what decision the screen supports.
2. Inspect user-supplied references in a real browser when possible. Capture at
least an opening composition and a representative deeper state for motion sites.
If inaccessible, use an attributable creator case study and label the limitation.
A URL or search snippet is not evidence of its full animation behavior.
3. Find a small reference set: one domain/flow reference and one visual or motion
reference when relevant. Prefer actual products, their official documentation and
creator portfolios over gallery thumbnails. Record URL, inspected state, reusable
principle, what must differ for this product, and assets/code licensing separately.
Do not copy branding, testimonials, screenshots or proprietary art into output.
4. Write a short decision note: user job; content hierarchy; reference observation;
chosen visual principle; asset plan; expected interaction. This is an accountable
design rationale, not a request for hidden chain-of-thought or a lengthy essay.
If research tools are unavailable, use real local material and label the gaps.

## Own the design foundations

- Colors: define canvas, surface, primary text, secondary text, border, action,
focus and status roles. Derive a brand accent from actual branding when present.
Check foreground/background contrast for each used pair, not a palette in isolation.
Dark interfaces still need distinguishable layers. Do not sprinkle random gradients.
- Typography: select fonts by product tone, reading density, language coverage,
number shapes and available weights. Reuse licensed local fonts first. Use one
family where enough, or a deliberate display/body contrast; set semantic roles,
line-height, line length, wrapping and tabular figures. Inspect real browser text.
Do not use a fashionable pairing without relating it to the content.
- Icons: choose one coherent licensed family by platform and stroke/fill behavior.
Map names to actions; inspect 16/20/24px legibility. Use custom SVG only when a real
concept is missing; original vectors need consistent viewBox, optical weight and
meaning. Hide decorative icons; label icon-only controls.
- Assets: map each slot to meaning, crop and resolution. Use real product assets,
licensed relevant photography, original illustration/vector or authorized generation
as appropriate. AWSM's make_asset is an SVG template utility, not a photo model.
Missing image tools do not justify fake screenshots, random stock or invented data.
- Backgrounds: choose purposeful depth: art-directed image field, material/texture,
section color rhythm, technical diagram, restrained shader or layered scene.
A plain surface can be correct for a task-heavy table; an immersive product story
needs an environment with subject placement, contrast and transitions. Decoration
must have a content reason and must not compete with labels or controls.

## Deliver without dumping process

Provide a brief direction sentence and implement the scoped flow. Keep a compact
source/decision ledger in project handoff when the work warrants it. Verify with
actual rendered states. Do not call a design premium solely because tokens exist.
